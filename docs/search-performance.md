# 전체 일기 검색 성능 측정

2026-10-20, Windows ARM64 / Snapdragon X1E80100 12코어, Rust 1.100.0-nightly.
`cargo test --release`로 측정했다. 모델은 CPU 2스레드의 multilingual-e5-small이며,
공개 모델 파일은 미리 다운로드했다. 개인 일기는 사용하지 않았다.

## 측정 방법

합성 일기 80개, 문단 240개, 검색어 3개를 사용한다. Org/Markdown과 LF/CRLF를 섞었다.
각 시나리오를 3회 측정하고 중앙값을 사용한다. 반복 검색은 검색어 3개 × 3회, 총 9회다.

- 최초 색인: 모델 세션과 임베딩 캐시가 없는 검색. OS 파일 캐시를 비운다는 뜻은 아니다.
- 반복 검색: 같은 검색 인덱스와 모델 세션을 재사용한다.
- 재시작 재현: 인덱스와 모델 세션을 버린 뒤 같은 저장소에서 새로 만든다. OS 프로세스 자체를 재시작하는 측정은 아니다.
- 수정 후: 기존 일기 하나에 새 문단을 추가한다. 해당 일기의 문단 4개만 재계산한다.

시간은 파일 읽기·문단 분할·캐시 복원을 포함한 refresh, 모델 로딩, 문단 임베딩,
캐시 저장, 검색어 임베딩, 문자열 검색·순위 계산으로 구분한다.
표의 합계는 검색 엔진 시간이다. TUI 이벤트 전달·최대 50ms 폴링·렌더링과 검증 코드는 제외했다.
각 단계의 중앙값을 더한 값과 전체 시간의 중앙값은 다를 수 있다.

## 측정 결과

| 시나리오 | 개선 전 | 개선 후 | 해석 |
|---|---:|---:|---|
| 임베딩 캐시 없는 최초 색인 | 3,902.65 ms | 3,662.33 ms | 소폭 감소; 모델 로딩 변동도 포함 |
| 같은 실행 중 반복 검색 | 11.66 ms | 12.27 ms | 거의 동일 |
| 인덱스·모델 세션 재생성, 캐시 재사용 | 3,877.67 ms | 1,264.85 ms | 약 3.07배, 67.4% 시간 감소 |
| 일기 하나 수정 후 | 49.18 ms | 55.30 ms | 캐시 저장과 실행 변동으로 약 6 ms 증가 |

최초 색인의 단계별 시간은 다음과 같다.

| 단계 | 개선 전 | 개선 후 |
|---|---:|---:|
| 파일 읽기·캐시 확인 | 7.20 ms | 9.83 ms |
| 모델 로딩 | 1,488.01 ms | 1,253.88 ms |
| 문단 임베딩 | 2,402.32 ms | 2,287.69 ms |
| 캐시 저장 | 없음 | 118.67 ms |
| 검색어 임베딩 | 4.39 ms | 4.95 ms |
| 문자열 검색·순위 계산 | 0.36 ms | 0.31 ms |

최초 색인의 문단 추론 호출은 80회에서 15회로 줄었다. 캐시 재사용 시에는 문단 추론이
240개/80회에서 **0개/0회**가 되고, 복원·파일 확인 약 18.55 ms와 모델 로딩 약 1,241.21 ms가 남는다.
일기 수정 후에는 두 구현 모두 해당 일기의 문단 4개만 추론하며, 개선 후에는 캐시 저장 약 1.97 ms가 추가된다.
최초 색인의 절대 개선 폭은 작다. 고정 비교 경로 재측정에서도 초기 색인 중앙값은 3.70초여서,
초기 색인 전체 시간 차이만으로 배치 처리 효과를 과장하지 않는다.

같은 모델 세션에서 240개 문단을 처리한 별도 배치 실험은 다음과 같다. I/O·모델 로딩은 제외한다.

| 처리 방식 | 문단 임베딩 중앙값 |
|---|---:|
| 일기별 3개씩 | 2,521.34 ms |
| 길이 구분 없이 32개씩 | 2,459.18 ms |
| 비슷한 길이 8개씩 | 2,266.37 ms |
| 비슷한 길이 16개씩 | 2,159.94 ms |
| 비슷한 길이 32개씩 | 2,512.19 ms |

이 환경에서는 비슷한 길이의 16개 배치가 가장 빨라 최종값으로 선택했다. 호출 수 감소가
동일한 비율의 처리 시간 감소를 보장하지는 않는다. 모델·하드웨어를 바꾸지 않았으며,
다른 CPU나 문단 길이 분포에서도 16이 최적이라고 주장하지 않는다.

3회 원시 표본과 검증 집계는 [측정 데이터](search-performance-results.json)에 보관한다.

## 개선 내용

`entries/.search-cache/<날짜>.json`에 SHA-256 원문 지문, 모델/분할 버전, 384차원 벡터를 저장한다.
본문·검색어·문맥 문자열은 중복 저장하지 않는다. 원문은 매번 읽어 확인하므로 파일 길이나 수정 시각이
같은 외부 수정도 감지한다. 모델/분할 버전, 지문, 문단 수, 벡터 차원·유한성·노름을 검증한다.
손상 캐시는 다시 계산하고, 캐시 I/O 실패는 원문이나 검색 결과를 잃지 않도록 안내 후 계속한다.
삭제된 일기의 캐시는 다음 검색에서 정리한다.

미처리 문단은 비슷한 길이끼리 묶어 일기 경계를 넘어 최대 16개씩 추론한다. 원래 문단의 참조로 결과를 돌려주므로
원문의 행·열은 유지된다. 파일·디렉터리 링크 거부, 크기 제한, 임시 파일과 원자적 교체는 기존 저장 계층을 재사용한다.
Unix에서는 기존과 동일하게 비공개 디렉터리·파일 권한을 사용한다.

파일 읽기와 결과 정렬은 이번 측정에서 초기 지연의 주요 원인이 아니어서 유지했다.
의미 모델, 검색 점수, 결과 개수와 정렬 규칙도 유지했다.

## 재현

테스트 코드의 `baseline_refresh`와 `baseline_embed_documents`는 개선 전 경로를 고정해 둔 비교군이다.
다음 PowerShell 명령은 현재 체크아웃에서 두 경로를 순서대로 실행한다.

```powershell
$env:DIARY_SEARCH_BENCH_PHASE = 'before'
cargo test --release -p diary-runtime search_release_benchmark -- --ignored --nocapture
$env:DIARY_SEARCH_BENCH_PHASE = 'after'
cargo test --release -p diary-runtime search_release_benchmark -- --ignored --nocapture
Remove-Item Env:DIARY_SEARCH_BENCH_PHASE

cargo test --release -p diary-runtime search_batch_sizes -- --ignored --nocapture
```

모델이 캐시되어 있다면 `HF_ENDPOINT=http://127.0.0.1:9`로 설정해 네트워크 없이 실행할 수 있다.
실제 검증도 이 설정을 사용했다. 처음 모델을 받을 때는 이 설정을 사용하지 않는다.
원시 결과는 `target/search-benchmark-before.json`, `target/search-benchmark-after.json`,
`target/search-batch-sizes.json`에 저장한다. JSON에는 단계별 시간, 추론 호출 수와 문단 수,
결과의 날짜·행·열·종류·anchor·excerpt를 기록한다. 비교군은 최적화 전 실제 코드에서 먼저 측정했고,
고정된 비교 경로를 재실행했을 때 결과 스냅샷이 일치하는 것도 확인했다.

## 정확성 검증

개선 전후 18개 검색 시나리오의 결과 600개에서 순서, 날짜, 행·열, 문자열/의미 구분,
anchor와 excerpt가 모두 일치해야 벤치마크가 통과한다. 각 단계에서 모든 결과를 Emacs와 Helix로
실제로 열어 에디터의 날짜·커서 위치를 확인한다. 최종 개선 경로에서 1,200회 위치 이동을 검증한다.
이 검증은 검색 시간 측정 후에 실행한다.

일반 테스트는 캐시 재시작 복원, 같은 길이의 본문 수정, 삭제, 다른 저장소 격리,
캐시 손상·버전·지문·차원·영벡터 오류, 읽기 전용 캐시 파일, 파일·디렉터리 심볼릭 링크 거부를 확인한다.
기존 원문 이동 테스트는 검색 후 문단 이동·삭제, 한국어 열 위치, LF/CRLF, 저장 동작도 확인한다.

## 남은 범위

첫 검색의 모델 세션 로딩은 여전히 필요하다. 실제 일기 수·문단 길이·CPU에 따라 시간이 달라지며,
80개 합성 일기의 수치를 대규모 저장소나 실제 사용자의 일기 성능으로 일반화하지 않는다.
모델 변경·GPU·근사 벡터 DB·파일 감시는 추가하지 않았다. 모델 선행 로딩은 아래 후속 개선에 포함했다.

## 후속 개선: 첫 화면 이후 모델 선행 로딩

첫 화면을 그린 뒤 기존 검색 스레드에서 모델을 미리 로딩한다. `Runtime::start()`와 첫 프레임은
모델을 기다리지 않는다. 같은 스레드가 준비된 모델로 검색을 수행하므로 로딩 중 검색 요청을 받아도
별도 모델 인스턴스를 만들지 않는다. 여러 대기 요청은 기존과 같이 최신 검색어만 처리한다.
준비 실패는 시작 화면 팝업을 띄우지 않고 실제 검색에서 다시 시도하며, 계속 실패하면 문자열 검색 결과를 제공한다.
스레드 생성 실패도 실제 검색 경로에서 재시도·보고한다. 종료 시 모델 준비 완료를 기다리는 join은 하지 않는다.

릴리스 검색 엔진 벤치마크는 같은 80개 합성 일기·240개 문단의 영구 캐시를 미리 만든 뒤,
새 작업 스레드의 첫 검색을 3회 비교한다. 모델 다운로드는 제외했고 네트워크가 없는 설정으로 검증했다.

| 항목 | 중앙값 |
|---|---:|
| 선행 로딩 없이 첫 검색 | 1,230.56 ms |
| 선행 로딩 요청의 호출자 반환 시간 | 0.107 ms |
| 백그라운드 모델 준비 완료까지 | 1,211.45 ms |
| 준비 완료 후 첫 검색 | 21.51 ms |
| 모델 준비 직후가 아니라 앱 실행 직후 즉시 검색 | 1,248.43 ms |

모델 로딩 자체를 제거한 것이 아니라 첫 검색보다 먼저 수행한다. 준비 완료 후 검색 대기는 약 57배 줄지만,
앱 실행 직후 바로 검색하면 남은 로딩 시간을 기다린다. 문단 캐시가 없는 경우에는 여전히 색인 시간이 필요하다.
검색 시간은 요청 전달부터 작업 스레드의 결과 응답까지이며 TUI 결과 표시의 최대 50ms 폴링은 제외한다.
선행 로딩 완료 후 3개 검색어와 로딩 중 제출한 검색어까지 총 15개 응답을 기준 결과와 비교해 순서·구절·위치가 일치했다.

TUI 검증은 실제 모델을 로딩하면서 `run_app`과 100×28 `TestBackend` 렌더러를 실행했다.
설정 열기·닫기, 크기 변경, 일기 열기·한국어 입력·저장·달력 복귀·종료를 5ms 간격으로 전달하고
입력 전달부터 다음 프레임 렌더링 완료까지 측정했다. 각 조건 3회, 회당 48프레임이다.

| 항목 | 선행 로딩 없음 | 선행 로딩 있음 |
|---|---:|---:|
| 첫 프레임 중앙값 | 0.365 ms | 0.335 ms |
| 실행별 입력 지연 중앙값의 중앙값 | 0.121 ms | 0.146 ms |
| 실행별 입력 p95의 중앙값 | 0.691 ms | 0.273 ms |
| 모든 실행의 최대 입력 지연 | 14.602 ms | 14.767 ms |
| 최대 종료 처리 시간 | 0.0025 ms | 0.0009 ms |

미리 로딩 스케줄링은 첫 프레임 이후이며 TUI 측정의 호출자 비용은 중앙값 0.053ms였다.
초기 화면 지연이나 입력 지연의 실질적 악화는 관측하지 않았다. 수치는 OS 프로세스 실행·실제 터미널
초기화·설정 파일 I/O를 포함한 전체 앱 시작 시간이 아니라 합성 저장소의 화면 루프 첫 프레임까지다.
입력/출력 드라이버는 테스트로 대체했지만 실제 애플리케이션 키 처리·파일 저장·화면 렌더링을 사용한다.
정밀한 p95 차이는 작은 표본·OS 스케줄링 변동이 있으므로 속도 향상으로 해석하지 않는다.
로딩을 의도적으로 멈춘 결정적 테스트에서도 다른 스레드 실행, 중복 방지, 편집·저장·종료,
대기 검색 최신 요청 처리, 첫 프레임 이후 1회 스케줄링과 불필요한 재렌더링 방지를 검증했다.

측정 데이터는 [선행 로딩 결과](search-preload-results.json)에 보관한다.

```powershell
$env:HF_ENDPOINT = 'http://127.0.0.1:9' # 모델 파일이 이미 캐시된 경우만
cargo test --release -p diary-runtime search_preload_benchmark -- --ignored --nocapture
cargo test --release -p ratatui-diary --bin ratatui-diary preload_tui_benchmark -- --ignored --nocapture
Remove-Item Env:HF_ENDPOINT
```

일반 테스트는 실제 모델을 로딩하거나 다운로드하지 않는다. 선행 로딩은 모델 메모리를
앱 시작 후부터 사용한다는 비용이 있으며, 실제 터미널과 다른 CPU의 체감 지연은 따로 측정하지 않았다.
